# ADR-015: Make event tools independently reusable by organizers and their coding assistants

**Status:** Proposed

**Date:** 2026-11-23

## Context

Showing the tools to another organizer raised the question of independent hosting. SDLCAI already supports multiple editions under one administration. Each edition gets its own database, storage and staff links. The admin credentials and news subscriptions span the installation. The catalog requires a 2026 entry, and the route allowlist determines which workspaces another edition can open. [ADR-014](../implemented/ADR-014-separate-event-administration-from-shared-tools.md) · [Event catalog and allowlist](../../../worker/event-workspaces.ts) · [Scope inventory](../../event-administration.md)

Cloudflare coupling extends beyond deployment. Of 71 TypeScript files directly under `worker/`, 58 mention the platform `Env` type, 44 name the `INTERESTS` database binding and six instantiate `HTMLRewriter`. Importing the application entry point also imports the Q&A Durable Object classes and a social renderer that reads the Workers cache at module load. Turning off their routes would still load those dependencies. [Worker entry point](../../../worker/index.ts) · [Social renderer](../../../worker/social-renderer.ts) · [Bindings](../../../wrangler.jsonc)

An edition-independent route can still produce SDLCAI-specific output. The catering export prints the October 2026 date and Marsio venue, attendee messages use SDLCAI's sender and reply address, and proposal consent names Toska. Speaker IDs and talk assignments come from the bundled programme even when the mutable content lives in the database. [Catering export](../../../site/scripts/attendee-diets.ts) · [Event messages](../../../worker/attendee-messages.ts) · [Proposal consent](../../../worker/poster-proposals.ts) · [Canonical speaker content](../../../worker/canonical-content.ts)

## Trigger

An organizer with an existing application should be able to point their coding assistant at this repository and ask it to add one capability, such as printing name badges from their own roster.

## Proposed decision

Make the unit of adoption an independently consumable building block. SDLCAI will consume those same blocks and supply its event data, access rules and Cloudflare services. An organizer can use one block in their own application or compose several. SQLite is the reference database for blocks that persist data. Rendering badges from supplied records runs entirely in the browser.

### Interfaces for people, assistants and applications

Offer a human UI and a Model Context Protocol (MCP) interface for each released workflow. Keep the underlying operations callable from code so an adopter can embed a block in an existing application. Someone pointing their coding assistant at the repository can integrate the package. Someone connecting an assistant to a running toolkit can operate the enabled blocks immediately.

Each block owns its input validation, decisions, results and errors. The UI presents those results to a person. The MCP server exposes task-level tools with documented input and output schemas and registers only enabled blocks. The catalog links to the UI entry point, MCP setup and tools, and package example. An adopter can enable the interfaces they use independently. [MCP server concepts](https://modelcontextprotocol.io/docs/learn/server-concepts)

| Badge task         | Human UI                                                                                   | MCP                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Check a print run  | Preview the actual artwork and show fit or missing-glyph issues beside the affected badge. | `badges_preflight` takes the same badge rows, branding and settings. It returns page count, physical dimensions and issues keyed to the input row. |
| Produce the output | Prepare the sheets and let the person print or save a PDF from the browser.                | `badges_export_pdf` reruns the checks and, on success, returns the page summary and a resource link to the PDF that the caller can retrieve.       |

The tool names are proposed. Both interfaces use the same artwork, font metrics and print rules. The UI uses the person's browser. For the pilot, the MCP server runs locally and uses headless Chromium to produce the PDF. Rendering needs no database. This gives the assistant a deliverable it can hand to the organizer for inspection or printing. [Studio print workflow](../../../site/scripts/admin-badges.ts) · [MCP tool results and resource links](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool-result)

For a stateful block, carry the caller's identity, permissions and event scope into the same operation from either interface. For example, an organizer editing a directory entry through MCP supplies the revision they read. A colleague with an older revision open in the UI gets a conflict when saving. Both changes use the same storage adapter and access rules. [Organizer directory](../../../worker/organizers.ts)

### How a coding assistant finds and uses a block

Put a short task catalog at the repository entry point. Use the organizer's vocabulary, with entries such as **Print name badges**, **Count lanyards by role** and **Import a registration CSV**. Mark the maturity of each entry and its interfaces. List a workflow as available when its package example, UI and MCP tools pass the consumer checks against the distributed files. Today these are extraction candidates.

Each available entry should answer four questions.

1. **Does it fit my task?** State what the block produces, its runtime, required inputs and assets, optional integrations, and relevant limits. For badges, describe round artwork, supported roles, font coverage, and browser print or save-as-PDF.
2. **What do I install and call?** Link to a versioned release or package, its public exports and the smallest working example. Use exported types and runtime validation as the source for field names, units and defaults. Ship required styles and assets, including their reuse terms.
3. **Where does my application connect?** Identify the fields to map, the settings to customize and any storage or service operations the caller supplies. Keep example records fictional. Provide one failure example and show how the caller reports or corrects it.
4. **How do I verify the integration?** Give one command with an observable expected result. Run that recipe in CI from a clean consumer project against a packed block. This catches private imports, missing fonts and examples that accidentally rely on the SDLCAI checkout.

### Printable name badges as the first block

The artwork renderer already reads only `name`, `company` and `role` to produce an SVG and layout issues. Its public TypeScript signature currently requires the full admin roster record. The studio also supplies print sheets, page breaks, preflight and physical dimensions. Extract those together so an adopter can go from a row to a printable badge without rebuilding the print setup. [Badge renderer](../../../site/scripts/badge-layout.ts) · [Badge model](../../../site/scripts/badge-model.ts) · [Studio printing](../../../site/scripts/admin-badges.ts)

| The caller supplies                                                                                                                                                      | The badge block supplies                                                                                                                                                                                                    | SDLCAI supplies in its own integration                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Display name, company text (which may be empty) and role for each named badge, optional spares, event logo, and print settings such as diameter and bleed in millimetres | SVG previews, font and fit checks, per-badge issues, and a print-ready sheet per badge or side. Package the default font and its license, accept branding and role appearance, and wait for fonts and logo before printing. | Authenticated roster reads, selection and duplicate-email review, source refresh before printing, encrypted saved preferences, and compatibility with past badge runs. |

For example, a consumer row could be `{"name":"Zoë Marin","company":"Field Notes","role":"speaker"}`. Rendering that badge needs no email, ticket identity, account or database. The current font and logo use absolute site paths, the printer preloads the same hard-coded logo, and the model infers an affiliation from an email domain. Resolve assets from the block or its caller and leave that inference in the SDLCAI integration. [Font and artwork](../../../site/scripts/badge-layout.ts) · [Font license](../../../assets/badges/OFL.txt) · [SDLCAI roster and preferences](../../../worker/badge-workspace.ts)

Use a release artifact that can be installed in a fresh project. A locally packed package is enough for the pilot; the root package is private. Choose source reuse terms before offering a public release. [Current package](../../../package.json)

#### How the pieces fit

For an organizer who asks “Print badges and tell me what to order from this ticket export,” the importer reads their CSV. Their application selects the included people and maps name, company and role into the badge generator. The lanyard planner uses the same selection plus spare quantities. A customer who already has a roster can start at that second step. Someone adding a registration desk later can persist ticket identities and arrivals in SQLite without changing the artwork API.

Keep the mapping in the consuming application. For example, SDLCAI maps volunteers onto an organizer badge, merges some poster presenters with tickets, and checks source revisions before printing. The check-in workflow preserves an earlier arrival when a ticket is linked. These rules belong to the relevant integration or stateful workflow. The artwork block only needs the text, role and print settings. [Roster reconciliation](../../../worker/event-attendees.ts) · [Source revision triggers](../../../migrations/0026_link_event_registration_sources.sql) · [Studio inputs](../../../worker/badge-workspace.ts)

### Hosting contracts

Let a feature take the operations it needs. For example, the organizer directory needs an ordered read and revision-checked writes. A check-in needs a single operation that validates the staff grant and roster revision and records the arrival atomically. D1 and native SQLite can share appropriate SQL behind those operations. Keep provider SDKs, binding lookup, CLI migrations and deployment in the host adapter. The entry point should load only enabled modules and verify their required services. [Organizer directory](../../../worker/organizers.ts) · [Atomic assignment and check-in](../../../worker/attendees.ts) · [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

| Current dependency                                               | What a second host needs                                                                                                                                                                                                                                                         |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker fetch, static assets, HTML rewriting, cache and client IP | A Fetch-style request entry point, authenticated asset delivery, event-aware views and links, private cache headers, and a trusted source of client addresses for throttling. The current build contains protected files. The host must apply authorization before serving them. |
| Cron and `waitUntil`                                             | A job runner for hourly and daily work and a way to finish deferred work after a response. Run newsletter jobs once per installation and event jobs against each enabled event's resources.                                                                                      |
| R2 uploads, exports and backups                                  | Separate private storage scopes. A filesystem or S3-compatible implementation must preserve the operations each workflow uses, including ranged reads for video and conditional writes for backup manifests.                                                                     |
| Email, Turnstile and Mailrelay                                   | A transactional mail sender, a form challenge with both widget and server verification, and an optional newsletter sync provider. Isolate sender identity, rate limits and suppression handling from the host choice.                                                            |
| Q&A Durable Objects                                              | Serialized room mutations and persisted state, plus staff throttling. Existing clients support polling, so a single-server implementation can introduce live notifications later.                                                                                                |
| Images, Stream and Browser Rendering                             | Optional image processing, private video upload and verified processing callbacks, and graphic rendering. Load providers only for the features that use them.                                                                                                                    |

These contracts come from the paths that serve protected HTML, publish backup manifests, stream media and refresh Q&A. The current Cloudflare adapter should continue to exercise those paths as each module moves. ## Pilot and acceptance

1. **Print from an unrelated project.** Give a coding assistant a clean project, the catalog link and the request “Print round badges for my two speakers and one spare attendee badge with our logo.” It should find the block, map the fictional records and run its documented example using only the packed artifact and public API. Check that the browser uses the new logo, prints three pages, and prints six with repeated backs. A 100 mm diameter and 3 mm of bleed per edge should yield 106 mm square pages, within browser rounding. A missing glyph must identify the affected badge and block printing. This exercises both discovery and the delivered files. [Existing print checks](../../../scripts/validate-badges.mjs)
2. **Exercise the UI and MCP from the packed release.** With the same fictional roster, logo and settings, use the browser UI and have an MCP client discover the tools, call preflight, export and retrieve the PDF. Inspect both outputs for three 106 mm pages, the supplied names and logo. Run the missing-glyph case through both and verify that each identifies the same row and withholds print-ready output.
3. **Use the same block in SDLCAI.** Wire the badge studio to the public API. Run its existing tests for source refresh, duplicate review, spare quantities, saved preferences, legacy records and real PDF pagination. This keeps the production studio and the documented example on the same implementation. [Badge unit tests](../../../test/badges.test.mjs) · [Studio integration scenarios](../../../test/organizers-badges.integration.test.mjs)
4. **Test storage with a stateful block.** The organizer directory is a small second candidate. Give it a narrow storage interface, a native SQLite reference implementation with its own migrations, and a D1 adapter. On each backend, edit an entry through MCP, read it in the UI and verify an older UI edit is rejected. Check that a caller without permission is denied through either interface. [Organizer directory](../../../worker/organizers.ts)

### Evidence so far

In a standalone Chromium page, the current renderer produced two 100 × 100 mm SVG badges from fictional records and the browser generated a two-page PDF. Both names passed layout checks, and an unsupported character produced a font-coverage issue. The probe transpiled the modules, provided print CSS and served a neutral logo at the expected site path. It ran without the Worker, database or Gustwind. The five existing badge unit tests also passed on Node 24. The independent package, its consumer recipe and the assistant-led acceptance run are proposed deliverables. [Badge tests](../../../test/badges.test.mjs) · [Browser scenarios](../../../scripts/validate-badges.mjs)

For storage, the earlier probe applied the existing empty-event bootstrap to native SQLite on Node 24.22.3. The organizer admin guard and handler returned 401 for an anonymous read, supported authenticated edits, and returned 409 for a stale revision. A volunteer-handler probe also exercised encrypted persistence. Those results support starting with SQLite for stateful blocks. [Empty-event bootstrap](../../../scripts/event-database.mjs) · [Schema test](../../../test/event-workspaces.test.mjs)

## Consequences and alternatives

An external consumer adds a packaging and compatibility obligation for each public API. Start with one tested distribution and use the SDLCAI application as a consumer. A whole-site starter may eventually help organizers who need several workflows, but it would make a single-feature adopter learn the site's hosting and data model. A source-file index alone would help an assistant locate code while leaving it to infer asset paths, runtime dependencies and printing behavior. The packed example tests those assumptions directly.
