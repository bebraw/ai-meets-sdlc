# ADR-015: Make event tools independently reusable by organizers and their coding assistants

**Status:** Implemented

**Date:** 2026-11-23

## Context

Showing the tools to another organizer raised the question of independent hosting. SDLCAI already supports multiple editions under one administration. Each edition gets its own database, storage and staff links. The admin credentials and news subscriptions span the installation. The catalog requires a 2026 entry, and the route allowlist determines which workspaces another edition can open. [ADR-014](../implemented/ADR-014-separate-event-administration-from-shared-tools.md) · [Event catalog and allowlist](../../../worker/event-workspaces.ts) · [Scope inventory](../../event-administration.md)

Cloudflare coupling extends beyond deployment. Of 71 TypeScript files directly under `worker/`, 58 mention the platform `Env` type, 44 name the `INTERESTS` database binding and six instantiate `HTMLRewriter`. Importing the application entry point also imports the Q&A Durable Object classes and a social renderer that reads the Workers cache at module load. Turning off their routes would still load those dependencies. [Worker entry point](../../../worker/index.ts) · [Social renderer](../../../worker/social-renderer.ts) · [Bindings](../../../wrangler.jsonc)

An edition-independent route can still produce SDLCAI-specific output. The catering export prints the October 2026 date and Marsio venue, attendee messages use SDLCAI's sender and reply address, and proposal consent names Toska. Speaker IDs and talk assignments come from the bundled programme even when the mutable content lives in the database. [Catering export](../../../site/scripts/attendee-diets.ts) · [Event messages](../../../worker/attendee-messages.ts) · [Proposal consent](../../../worker/poster-proposals.ts) · [Canonical speaker content](../../../worker/canonical-content.ts)

## Trigger

An organizer with an existing application should be able to point their coding assistant at this repository and ask it to add one capability, such as printing name badges from their own roster.

## Decision

The unit of adoption is an organizer task. A single installable package contains 19 independently selectable blocks. Each block defines its operations, input and result schemas, fictional examples and access rules. Callers can use the package directly, run the human workspace, or connect a coding assistant over MCP. All three entry points call the same operations. [Catalog and setup](../../../toolkit/README.md)

### Interfaces

The browser builds forms from the input schemas and supplies task-specific views for people working at the door, guests, speakers, respondents and moderators. The MCP server lists only the tools available to its configured identity. A client can read the catalog, call an operation, inspect its structured result and retrieve private file artifacts on the same connection. A JavaScript caller receives artifact bytes directly. [Package API](../../../toolkit/index.mjs) · [MCP server](../../../toolkit/mcp.mjs)

For badge printing, the caller supplies names, roles, optional affiliations, spares, branding and physical settings. The shared artwork renderer measures text using the packaged font. Preflight reports the source row for each issue. Export repeats preflight and produces a physically sized PDF only when the run is ready. The standalone UI and MCP use the same local Chromium PDF renderer. The SDLCAI studio and browser integrations can import the underlying SVG renderer. [Print operations](../../../toolkit/blocks/print.mjs) · [Browser artwork](../../../toolkit/blocks/badge-artwork.mjs)

### Discovery and distribution

The repository README links to an organizer-facing catalog. Each operation provides machine-readable input and output contracts and sample input through the package API, CLI and MCP resource. Every block has a runnable example in the installed package. The quality workflow packs the distribution, installs it outside this repository, exercises both interfaces and attaches the tested tarball to the run. The font includes its own reuse terms. The package is marked `UNLICENSED` pending a source licensing decision for public distribution. [Installation and examples](../../../toolkit/README.md) · [Consumer check](../../../toolkit/checks/consumer.mjs)

#### How the pieces fit

For an organizer who asks “Print badges and tell me what to order from this ticket export,” the importer reads their CSV. Their application selects the included people and maps name, company and role into the badge generator. The lanyard planner uses the same selection plus spare quantities. A customer who already has a roster can start at that second step. Someone adding a registration desk later can persist ticket identities and arrivals in SQLite without changing the artwork API.

Keep the mapping in the consuming application. For example, SDLCAI maps volunteers onto an organizer badge, merges some poster presenters with tickets, and checks source revisions before printing. The check-in workflow preserves an earlier arrival when a ticket is linked. These rules belong to the relevant integration or stateful workflow. The artwork block only needs the text, role and print settings. [Roster reconciliation](../../../worker/event-attendees.ts) · [Source revision triggers](../../../migrations/0026_link_event_registration_sources.sql) · [Studio inputs](../../../worker/badge-workspace.ts)

### Hosting contracts

The reference host runs on Node.js 24 and stores event records in native SQLite. Each event has a separate database. Newsletter subscriptions share an installation database. Library callers can use ephemeral storage. The HTTP and MCP adapters pass event scope and a trusted principal into operations. Revision-checked writes protect concurrent edits, and desk check-in records each arrival atomically with the roster checks. [Runtime](../../../toolkit/index.mjs) · [SQLite adapter](../../../toolkit/storage.mjs)

The original site continues to use Cloudflare. Its organizer directory and the SQLite implementation execute the same ordered reads and revision-checked writes through a narrow repository interface. The site imports shared badge artwork, CSV parsing, lanyard counting, catering calculations and programme validation. Operator credentials, branding, SDLCAI roster reconciliation and legacy URL handling belong to the site. [D1 adapter](../../../toolkit/blocks/organizer-store.mjs) · [Site directory](../../../worker/organizers.ts)

For another host, the package accepts mail delivery, challenge verification and invitation URL generation through service interfaces. The reference CLI supplies optional SMTP and Turnstile implementations. A single host can serve Q&A updates through polling, store private PDF materials in the event database and produce graphics with local Chromium. The site's Cloudflare-specific integrations for Stream video, R2 backups, edge caching and Durable Objects continue to serve the SDLCAI deployment. [Host options](../../../toolkit/README.md#hosting-and-adapters)

## Verification

The packed-consumer check uses the published package exports and ships fictional event data with its own logo. It exercises all 19 blocks through the browser and stdio MCP, downloads real artifacts and checks page dimensions and row-specific errors. It also edits an organizer through MCP, reads that revision through the UI and checks stale updates. The site suite retains coverage for existing roster reconciliation, legacy badge records and the deployed Worker entry points. [Packed consumer](../../../toolkit/checks/consumer.mjs) · [Block tests](../../../toolkit/test) · [Site badge scenarios](../../../test/organizers-badges.integration.test.mjs)

## Consequences and alternatives

An external consumer adds a packaging and compatibility obligation for each public API. Start with one tested distribution and use the SDLCAI application as a consumer. A whole-site starter may eventually help organizers who need several workflows, but it would make a single-feature adopter learn the site's hosting and data model. A source-file index alone would help an assistant locate code while leaving it to infer asset paths, runtime dependencies and printing behavior. The packed example tests those assumptions directly.
